# Git workflow для изменений

Применяется к любому изменению кода и конфигурации проекта.

## Порядок

1. **Базовая ветка — спросить.** Перед созданием ветки спросить пользователя, от какой ветки бранчиться. Не выбирать самостоятельно, даже если ветка «очевидна» (текущая rc, develop, master).
2. **Отдельная ветка и worktree.** Каждая задача — своя ветка (`feat/...`, `fix/...`, `refactor/...`) в отдельном git worktree. В основном checkout изменения не делать.
3. **Отдельный агент.** Изменения пишет отдельный агент (Agent tool с `isolation: "worktree"`), выбранный по file scope из таблицы `## Agents` в `CLAUDE.md`. В промпте агента явно указать базовую ветку: `git switch -c <branch> <base>`, затем проверить `git log`.
4. **Ревью в отдельном агенте.** После изменений запустить `code-reviewer` отдельным агентом на диф `git diff <base>...HEAD`. Ревьюер код не меняет.
5. **Исправления итеративно.** Замечания ревью (BLOCKER/MAJOR, а MINOR — по решению) исправляет агент-исполнитель отдельным коммитом. Затем повторное ревью. Цикл — до вердикта APPROVE.
6. **Коммит и PR.** Коммиты в стиле репозитория, без упоминаний AI и `Co-Authored-By`. Push ветки и создание PR через `gh pr create --base <base>` в базовую ветку из п. 1.
7. **Мерж — спросить.** После создания PR спросить пользователя, мержить или нет. Без явного «да» не мержить.

## После мержа

- Удалить worktree (`git worktree remove`) и локальную ветку.
- Если базовая ветка ушла вперёд во время работы — перед ревью/PR сделать rebase на актуальную базу и перепроверить сборку.
